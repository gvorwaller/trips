## td-036f71 — searchable anchor pickers (06747f0)

`clearOnEdit` prop (default true keeps stage-an-item semantics for add-stop /

## td-9ae4dd — Share text trapped iOS users (cf28bf3)

Root cause: the Share text `<a>` navigated to the inline `text/plain` export;
in the installed standalone PWA that replaces the app shell with a chrome-less
text view with no way back (`md`/`ics` were fine — attachment disposition gets
the share sheet). Fix: buttons fetch the same endpoint (unchanged) and open a
dismissible modal — system Share…, Copy, Close, backdrop tap, Escape. New
`$lib/share.ts` (isIosStandalone lifted from AttachmentDownloadButton, typed
navigator.share wrapper, AbortError = quiet cancel). Review rounds added real
focus management (land on Close, Tab trap, restore-to-trigger on every close
path) and surfaced share-sheet failures instead of swallowing them. QA 9/9
with FNV-1a fingerprint proof that modal text == endpoint bytes. Owner
verifies on the actual iPhone PWA.

## td-947440 — multi-select "move under" (8899f2d + 46384cf)

Select toggle → per-row checkboxes (replacing the visited slot while active) →
sticky bulk bar with filtered destination picker → `itin-reparent-many`
backed by pure `computeReparentMany`: document-order append, ids inside a
selected subtree travel with it, union cycle check, one transaction, one
`applyChanges`.

The review rounds are the story — four passes, three concurrency P1s, each
hardening ALL tree writers, not just the feature:

1. **Delete TOCTOU**: `applyChanges` now proves the id-ordered `FOR UPDATE`
   prelock locked exactly the expected set and every UPDATE hit one row;
   drift throws typed `TreeConcurrencyError` and the transaction writes
   nothing. Previously a row deleted between snapshot and lock was silently
   skipped mid-reindex.
2. **Phantom inserts**: the row-count guard can't see a sibling INSERTed
   after the snapshot — a concurrent `nextSortOrder` MAX could commit a
   duplicate `sort_order` into a group being rewritten. Fix: per-
   (table, container) `pg_advisory_xact_lock` taken FIRST by every
   membership-changing writer — the five tree-sql entry points and inside
   `nextSortOrder`, which every insert path funnels through.
3. **Lock-order inversion**: `createPackingItemAt` took its list-wide row
   prelock before `nextSortOrder`, i.e. rows-then-advisory — a deterministic
   deadlock cycle against tree ops. `lockTreeContainer` is now exported and
   is that function's first statement. Global order everywhere:
   advisory → item rows → trips (extends td-36b55b).

Also from review: strict form parsing (malformed input rejects the batch
instead of quietly becoming a *different* valid move), typed 400/500 error
split (real failures stay observable), Clear in the sticky bar.

Five deterministic db tests cover the races — held-lock schedules sequenced
by polling `pg_locks` (never sleeps), including a direct assertion that the
queued packing insert holds zero row locks while waiting on the barrier.
QA 10/10 including a two-tab concurrent-delete error path; tap audit
3/9/238 targets, 0 violations (its family assertion now points at the
combobox, the one expectation td-036f71 had left stale).

Owner's on-device iPhone check the same day: Share text works; bulk move
functional but the destination dropdown clipped offscreen (the sticky bar
sits at the viewport bottom, options dropped DOWN). Follow-up `fbdb383`:
scoped override opens the picker's options upward. Lesson for any control
living in a bottom-anchored bar: the combobox's drop direction is a layout
assumption, not a given.
